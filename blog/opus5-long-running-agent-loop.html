Claude Opus 5 and the Long-Running Agent Loop

Edoworks factory notes · August 3, 2026

On July 24, 2026, Anthropic announced Claude Opus 5, describing it as a step change improvement for the Opus tier that powers long-running agents while delivering improvements in coding and professional work. The announcement focuses on the model's ability to sustain agent workflows over extended sessions, which is the core capability a software factory needs.

The Edoworks factory operates on a plan, build, review, and verify loop. An agent receives an intent, plans an approach, implements the change, submits to review, and runs verification before reporting completion. The loop can repeat multiple times within a single session as review findings are addressed and verification is re-run. A model that can sustain this loop without losing context or degrading in quality is the kind of model that makes autonomous software production practical.

What Long-Running Agents Need

A long-running agent is not just a model with a large context window. It is a model that can maintain coherent intent across many tool calls, retain the results of earlier steps, and make consistent decisions as the session grows. The failure mode for agent loops is context drift: the agent forgets why it started, repeats work it already completed, or contradicts a decision it made earlier in the session.

Anthropic's announcement emphasizes long-running agents as a primary use case for Opus 5. The implication is that the model was trained or fine-tuned to maintain coherence over multi-step workflows, not just to perform well on single-turn tasks. For a factory, this matters because the factory's unit of work is the session, not the prompt.

Factory rule: The unit of work is the session, not the prompt. A model that degrades over a 50-step session is less useful than a model that stays coherent over 50 steps, even if the latter is slower per step.

How the Factory Loop Maps to the Agent Loop

The factory's plan, build, review, verify loop maps directly to what a long-running agent needs to sustain. Plan is the intent and approach phase: the agent reads the task, inspects the codebase, and proposes an approach. Build is the implementation phase: the agent makes the changes. Review is the checkpoint phase: an independent reviewer checks the diff. Verify is the evidence phase: tests, lint, type checks, and other validators run to confirm correctness.

Each phase is a checkpoint, not just a step. If review finds issues, the loop returns to build. If verification fails, the loop returns to build. The agent that sustains this loop is the one that can handle the return trips without losing the thread. A model that works well on the first pass but degrades on revision cycles is less useful for a factory than a model that stays coherent across multiple revision cycles.

Why Opus 5 Matters for Factory Operations

The factory's autonomy ratio depends on how much of the loop the agent can handle without human intervention. A model that can plan, build, address review findings, and run verification autonomously increases the autonomy ratio. A model that needs human help at each checkpoint keeps the ratio low.

Opus 5's emphasis on long-running agents suggests that the model is designed to handle more of the loop autonomously. The factory's review and verify steps remain as checkpoints, but the agent's ability to address findings and re-run verification without losing context reduces the human intervention needed at each checkpoint. That is the practical meaning of a step change for long-running agents.

The Cost Dimension

Long-running agents consume more tokens than single-turn prompts. A 50-step session with tool calls, file reads, and revisions can easily consume hundreds of thousands of tokens. The cost of a long-running agent session is higher than the cost of a single prompt, but the value is also higher if the session produces accepted, verified work.

The factory's model governance policy selects the cheapest approved tier that can safely satisfy the task. For long-running agent sessions that touch architecture, security, or release workflows, a stronger model is justified. For repetitive, low-risk work, a cheaper model may be sufficient. The Opus 5 launch adds a new option at the top of the tier ladder, which means the factory can route the most demanding agent sessions to the model best suited for them while keeping cheaper models for simpler work.

What This Means for the Factory

The factory's response to Opus 5 is operational, not architectural. The plan, build, review, verify loop does not change. The checkpoints do not change. What changes is the model's ability to sustain the loop, which affects how much of the loop the agent can handle autonomously and how much human intervention is needed at each checkpoint.

The factory's next step is to evaluate Opus 5 on a representative session and measure autonomy ratio, review turnaround, and defect rate against the current model. If the evaluation shows a meaningful improvement in sustained coherence over multi-step sessions, the factory will route long-running agent work to Opus 5 while keeping cheaper models for short, low-risk tasks.
